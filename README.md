# Расчётно-пояснительная записка для курсовой работы по предмету «Проектирование высоконагруженных систем»

## 1. Тема и целевая аудитория

**Тип сервиса**: платформа интерактивных прямых трансляций (аналог Twitch).

**Основной функционал MVP**:

1. Регистрация и авторизация пользователей;
2. Создание канала и проведение прямой трансляции;
3. Просмотр прямых трансляций с адаптивным качеством видео;
4. Подписка на каналы и получение уведомлений о начале трансляции;
5. Общение в чате трансляции в реальном времени;
6. Просмотр каталога трансляций и поиск каналов;

**Ключевые продуктовые решения**:

1. Публичные трансляции можно смотреть без регистрации;
2. Качество видео автоматически изменяется в зависимости от пропускной способности сети пользователя;
3. Сообщения чата доставляются участникам трансляции в реальном времени;
4. Записи завершённых трансляций хранятся ограниченное время, а созданные пользователями клипы — до их удаления.
5. Просмотр записей завершённых трансляций и создание коротких клипов.

**Ключевые функции, характеризующие сервис**:

1. Проведение и просмотр прямых видеотрансляций;
2. Общение зрителей и автора трансляции в реальном времени;

**Целевая аудитория**: около 105 млн пользователей в месяц и 35 млн пользователей в день по всему миру. По внутренним данным Twitch, сайт посещают в среднем 105 млн пользователей в месяц, около 70% зрителей находятся в возрасте от 18 до 34 лет.[[1]](#source1) По данным Amazon Ads, ежедневно Twitch посещают в среднем 35 млн пользователей со всего мира.[[2]](#source2)

Для расчётов приняты следующие допущения:

### 3.1. Разбиение по доменам

| Домен | Назначение |
|---|---|
| `www.twitch-clone.com` | Веб-приложение и статика через CDN |
| `api.twitch-clone.com` | Авторизация, каталог, поиск, подписки и выбор региональной точки входа |

### 3.4. Маршрутизация по загрузке кластера

При открытии трансляции API возвращает адрес чата, при запуске эфира — ingest-адрес. Отдельного дополнительного запроса к Resolver не требуется: выбор выполняется внутри существующего API-запроса.

1. По IP пользователя определяется предпочтительный регион.
2. Проверяются health и загрузка соответствующего сервиса: число соединений, CPU и занятая полоса; для ingest также учитывается свободная мощность транскодирования.
3. Если каждый из показателей ниже 80% рабочего лимита, выбирается этот регион. Иначе проверяется следующий ближайший регион со свободной ёмкостью.
4. Внутри региона выбирается VIP с наименьшей относительной загрузкой пула. Данные мониторинга обновляются раз в 5 секунд.
5. Клиент получает основной и резервный адреса. Установленное соединение остаётся на выбранном сервере; на каждое сообщение или видеопакет выбор не повторяется.

Если все регионы достигли рабочего порога, система использует оставшийся запас до жёсткого лимита; при его исчерпании ограничивает новые подключения. Существующие трансляции не мигрируют автоматически.

Для OBS список ingest-адресов отображается в настройках канала. При отказе основной точки OBS переподключается к резервной. Наш API не предполагает, что стандартный OBS умеет вызывать собственный Resolver сервиса.

DNS возвращает региональные VIP; TTL — 60 секунд. Anycast применяется только на стороне CDN для `www` и `video`. Адреса API, WebSocket и RTMP — региональные unicast-адреса. При отказе основного API DNS переключается на резервный API в Ашберне после повышения резервных БД; уже открытые чаты продолжают работать, пока доступен поток сообщений.

### 3.5. Размещение постоянных данных

Core DB хранит профили, каналы, подписки и метаданные видео. Отдельная **Chat Master DB** во Франкфурте хранит все сообщения за последние 30 суток.

Сообщение поступает в Kafka один раз. Региональные потребители рассылают его зрителям, а отдельный consumer сохраняет в мастер-БД. Сбой записи БД не останавливает рассылку сразу: Kafka хранит события 24 часа и позволяет обработать их повторно.

```text
WebSocket gateway → Kafka chat.messages → региональная рассылка
                                      → Chat writer → Chat Master DB
```

При 3 646 исходных сообщениях/с и размере 400 байт поток записи истории составляет около 1,46 Мбайт/с без индексов и репликации. Миллионы доставок не становятся миллионами SQL-вставок.

## 4. Локальная балансировка нагрузки

### 4.1. Схема и механизм L4

Внутри ДЦ используются HAProxy в TCP-режиме и NGINX для API. CDN edge-узлы в локальную балансировку не входят.

```mermaid
flowchart TD
    A["API VIP: HAProxy + Keepalived"] --> N["NGINX: TLS и L7"]
    N --> API["API-сервисы"]
    C["Chat VIP: HAProxy + Keepalived"] --> W["WebSocket gateways: TLS"]
    W --> K["Kafka"]
    K --> D["Chat Master DB"]
    I["Ingest VIP: HAProxy + Keepalived"] --> G["RTMP/RTMPS gateways"]
    G --> T["Транскодирование"]
```

Каждый VIP обслуживается парой HAProxy **active/standby**. Проверяются процесс HAProxy и необходимые сетевые интерфейсы. Keepalived переносит VIP на standby через VRRP при отказе активного узла. Если нужны `N` рабочих узлов, разворачиваются `N` независимых пар — резервирование **N × 2**. Внутри каждого пула HAProxy выбирает backend по `leastconn` и проверяет доступность серверов.

Так задан механизм обоих уровней: API выбирает регион и конкретный VIP по загрузке, HAProxy распределяет новые TCP-соединения между backend-серверами. Обычный L4 не анализирует URL, поэтому API, чат и RTMP имеют разные VIP.

### 4.2. API и TLS termination

Для API TLS завершается на NGINX. Он маршрутизирует запросы к сервисам авторизации, каталога и подписок по URI и использует `least_conn`.

В тесте NGINX на 8 CPU получено 31 485 TLS TPS без Hyper-Threading.[[5]](#source5) Для проекта принимаются более низкие рабочие лимиты: **5 тыс. новых TLS-соединений/с**, **100 тыс. HTTPS RPS** и **40 Гбит/с** на узел. Это проектные лимиты, которые требуется подтвердить нагрузочным тестом.

Для верхней оценки каждый API-запрос создаёт новое TLS-соединение:

```text
N_TLS = ceil(10 000 / 5 000) = 2
N_RPS = ceil(10 000 / 100 000) = 1
N_network = ceil(30 / 40) = 1
N_NGINX = max(2, 1, 1) + 1 = 3
```

30 Гбит/с — консервативная верхняя граница всей категории «API и чат» из раздела 2. Реальный API-трафик будет ниже. Для обычных запросов используется keep-alive; для расчёта L4 принято до 100 тыс. одновременных API TCP-соединений — пик 10 тыс. RPS с резервом до 10 секунд жизни соединения.

### 4.3. WebSocket

HAProxy передаёт зашифрованное TCP-соединение WebSocket-шлюзу. TLS и WebSocket завершаются на gateway. Соединение закреплено за gateway до закрытия; сообщения канала доставляются через Kafka, поэтому пользователям одного канала не обязательно находиться на одном сервере.

Рабочий лимит одного L4-сервера — **700 тыс. клиентских TCP-соединений** и **40 Гбит/с**. Количество учитывает соединения клиентов; дополнительные соединения до backend и память под буферы должны входить в ресурсный бюджет сервера.

Например, для Европы:

```text
N_chat = ceil(1 312 500 / 700 000) × 2 = 4 L4-сервера
```

Это две независимые пары HAProxy с двумя VIP. На каждую пару приходится не более 700 тыс. клиентских соединений.

### 4.4. RTMP

Для ingest выделяется отдельный пул HAProxy. Он проксирует RTMP/RTMPS по `leastconn`; ключ трансляции проверяется ingest gateway. При RTMPS TLS также завершается на gateway, а не на L4-балансировщике. После приёма поток направляется на транскодирование и в live-буфер.

Для L4 ingest принимаются 2 × 100 GbE и рабочая полоса **160 Гбит/с** с запасом 20%. Здесь ограничитель — сеть:

```text
N_ingest_EU = ceil(346,5 / 160) × 2 = 6 L4-серверов
```

Получаются три active/standby-пары с разными VIP. API распределяет новые трансляции между ними по загрузке.

| **Итого** | **4** | **14** | **18** | **6** |

API-балансировщики Ашберна — заранее подготовленный резерв на полную нагрузку основного API. В штатном режиме клиентские API-запросы идут во Франкфурт.

N × 2 резервирует производительность L4, но не переносит TCP-состояние. При отказе HAProxy его WebSocket- и RTMP-соединения разрываются. После переключения VIP клиенты переподключаются; чат восстанавливает последние сообщения по `message_id`/`sequence`. HTTP-клиент повторяет безопасные запросы, а изменяющие операции используют idempotency key.

### 5.3. Размеры и QPS

Объёмы — логические, без индексов, реплик и backup. 1 Тбайт = 10¹² байт. Размеры строк и частота служебных чтений — проектные допущения. В таблице приведён глобальный пик: QPS чтения списка — один запрос, запись — одна изменённая строка; при batch физическое число SQL-запросов меньше.

| SESSIONS | до 105 млн | 160 | 0,016800 | 608 | 608 |
| CHANNELS | 7 млн | 384 | 0,002688 | 2 015 | 4 |
| FOLLOWS | 5,25 млрд | 64 | 0,336000 | 1 354 | 61 |

| VODS | 7 млн | 256 | 0,001792 | 100 | 70 |

Обоснование:

- При 90% попаданий в кеш чтение карточки: `7 986 × 10% ≈ 800 QPS`. USERS дополнительно читает авторизацию: `800 + 608 = 1 408`. CHANNELS дополнительно обслуживает поиск: `800 + 1 215 = 2 015`.
- Для FOLLOWS принято открытие списка подписок в 10% просмотров страниц: около 799 QPS. Ещё около 555 QPS — сканирование 16 секций при обработке 35 стартов эфира/с. Размер страницы до 500 записей; крупные каналы потребуют дополнительных страниц и отдельного запаса.
- В среднем 50 подписок на MAU: `105 млн × 50 = 5,25 млрд`. Сессии ограничены одной на MAU в расчётной модели. Для регистрации принято 100 тыс. новых пользователей/сутки, или около 4/с в пике.
- Два открытия чата на DAU в сутки дают около 2 431/с в пике; 90% обслуживает кеш хвоста, около 243 чтений/с остаётся мастер-БД.
- Старт и завершение 1 млн эфиров/сутки дают около 70 изменений/с. Метаданные старых эфиров сохраняются, пока на них ссылаются VOD/клипы; 365 суток — средняя оценка для расчёта.
- Для VOD и клипов в записи учтены создание и последующее удаление. Счётчики зрителей обновляются агрегатами раз в 5 секунд, а не SQL-записью на каждый просмотр.

### 5.4. Консистентность и горячие ключи

| Данные | Требование | Распределение нагрузки |
|---|---|---|
| Пользователи, сессии, подписки | Транзакции, уникальные login/email, read-after-write через primary | По user_id; у популярных каналов горячий обратный индекс подписчиков |
| Трансляции | Только один live-эфир на канал; атомарный старт/стоп | Чтения популярных каналов обслуживает кеш |
| Чат | Порядок внутри канала; подтверждение после надёжной записи в Kafka; история в SQL появляется асинхронно, цель lag до 5 с | Kafka key = channel_id; gateway выполняет fan-out своим зрителям; каждое сообщение сохраняется в SQL один раз |
| Файлы | Карточка готова после публикации файла и манифеста | Ключ объекта неизменяемый; популярные файлы кешируются |
| Кеши, поиск, счётчики | Устаревание карточек допустимо до 5 с; счётчики приблизительные | TTL, инвалидация, объединение одновременных промахов |
| Уведомления | Как минимум одна попытка, возможны дубликаты | Дедупликация по stream_id; сканирование подписчиков страницами |

При недоступности Kafka новые сообщения не подтверждаются как принятые. При недоступности мастер-БД writer повторяет запись, пока события сохраняются в журнале. Если отставание угрожает 24-часовому retention, приём новых сообщений ограничивается: молча терять историю нельзя.

## 6. Физическая схема БД

### 6.1. Размещение данных

Основные SQL-данные разделены на **Core PostgreSQL** и **Chat Master PostgreSQL**. Разделение изолирует запись чата от авторизации и каталога. Поиск каналов выполняется средствами PostgreSQL; отдельный поисковый кластер для MVP не требуется.

На физической схеме перечислены ключи доступа, секционирование и копии. Полный состав полей совпадает с логической схемой; новые производные поля и индексы приведены в таблице ниже.

```mermaid
flowchart TD
    A["API и workers"] --> P["PgBouncer: primary/read endpoints"]
    P --> C["Core PostgreSQL: users, sessions, channels, follows, categories, streams, vods, clips"]
    W["Chat writer"] --> Q["PgBouncer Chat"]
    Q --> M["Chat PostgreSQL: messages; PK day/channel_id/message_id; IDX channel_id/sequence; RANGE day"]
    C --> CR["Core sync-standby: Франкфурт"]
    C --> CD["Core async DR: Ашберн"]
    M --> MR["Chat sync-standby: Франкфурт"]
    M --> MD["Chat async DR: Ашберн"]
    A --> R["Redis Cluster: cache:key, tail:channel_id, node:id; hash slots"]
    K["Kafka chat.messages: key channel_id; 64 partitions; RF=3"] --> W
    A --> S["Ceph RGW: object_key; VOD, clips, images, manifests; EC 8+3"]
    S --> D["Асинхронная копия файлов в парном регионе"]
```

Стрелки реплик показывают копирование данных. Chat writer на схеме — consumer потока; WebSocket-шлюзы публикуют в Kafka и потребляют его независимо от SQL writer.

### 6.2. Таблицы и индексы

| Данные | Хранилище и индексы | Шардирование / резервирование |
|---|---|---|
| USERS | Core PostgreSQL: PK `user_id`; UNIQUE `login`, `email` | Без горизонтального шардирования; primary + локальная sync-standby + async DR |
| SESSIONS | Core PostgreSQL: PK `session_id`; UNIQUE `refresh_hash`; IDX `user_id`, `expires_at` | То же; истёкшие строки удаляются пакетами |
| CHANNELS | Core PostgreSQL: PK `channel_id`; UNIQUE `owner_id`, `stream_key_hash`; GIN `search_vector` | `search_vector` — производное поле name/title; обновляется вместе с каналом |
| FOLLOWS | Core PostgreSQL: PK `(user_id, channel_id)`; IDX `(channel_id, user_id)` | 16 HASH-секций по user_id внутри одного primary; обратная выборка читает 16 индексов |
| CATEGORIES | Core PostgreSQL: PK `category_id`; UNIQUE `name` | Без шардирования, справочник кешируется целиком |
| STREAMS | Core PostgreSQL: PK `stream_id`; IDX `(channel_id, started_at DESC)`; частичный UNIQUE `channel_id WHERE status='live'`; IDX `(category_id, started_at DESC) WHERE live`; IDX необработанных стартов | Без шардирования; старые метаданные удаляются после исчезновения ссылок |
| VODS | Core PostgreSQL: PK `vod_id`; UNIQUE `stream_id`; IDX `expires_at` | Без шардирования; файл удаляется фоновым worker |
| CLIPS | Core PostgreSQL: PK `clip_id`; IDX `(stream_id, created_at DESC)`, `(creator_id, created_at DESC)`, `(channel_id, created_at DESC)` | `channel_id` денормализован из исходной трансляции для быстрого списка клипов канала |
| MESSAGES | Chat PostgreSQL: PK `(day, channel_id, message_id)`; IDX `(channel_id, sequence DESC)` | RANGE по UTC-дню; 30–31 суточная секция; отдельный primary + sync-standby + async DR |
| Кеш карточек и чата | Redis Cluster: `entity:type:id`, `tail:channel_id`; hash/string/list | В каждом регионе 3 master + 3 replica; TTL и удаление старых сообщений |
| Реестр кластеров | Redis Cluster: `node:id`, поля heartbeat/load/capacity, TTL 15 с | Обновление каждые 5 с; во Франкфурт передаются heartbeat всех регионов; API использует локальный снимок реестра |
| Чат-события | Kafka: `chat.messages`, key `channel_id` | 64 partitions; RF=3, `acks=all`, `min.insync.replicas=2`; retention 24 ч |
| MEDIA_FILES | Ceph RGW, S3 API: уникальный `object_key` и диапазон байтов | Хеш объекта распределяет данные внутри региона; EC 8+3 по стойкам; async-копия в парный регион |
| LIVE_BUFFER и live-манифесты | NVMe + память media-серверов; `(stream_id, rendition, seq)` | Две копии в разных стойках; TTL 10 минут |
| WS_BUFFER | Память gateway, map по connection_id | Не реплицируется: клиент переподключается и получает хвост чата |
| CDN-кеш | Внешняя CDN: URL/версия/byte range | Повторно заполняется из origin; не источник постоянных данных |

PostgreSQL поддерживает HASH/RANGE-секционирование и удаление старых данных целыми секциями.[[6]](#source6) Это не распределяет таблицу по серверам: горизонтального шардирования SQL в текущем MVP нет. Core содержит около 0,529 Тбайт строк, Chat Master — 1,26 Тбайт; нагрузка записи позволяет начать с отдельных primary и масштабировать чтение репликами. Окончательное количество дисков и CPU проверяется нагрузочным тестом.

Для сообщений `day` вычисляется из серверного `created_at`. При повторной обработке события сохраняются исходные `message_id` и `day`; вставка идемпотентна по PK. `sequence` берётся из offset Kafka-партиции. Один канал всегда попадает в одну партицию; число партиций без миграции порядка не меняется.

### 6.3. Чат, кеши и видео

Для чата работает одна consumer group записи истории и по одной группе рассылки на регион. Сообщения читаются регионами по одному разу, затем WebSocket-шлюзы отправляют их своим клиентам. Миллионы индивидуальных доставок не проходят через Kafka как отдельные события.

Chat writer сохраняет сообщения пакетами до 100 или раз в 50 мс и подтверждает consumer offset после SQL commit. Повторное чтение после сбоя не создаёт дубликатов. У текущего primary одна локальная синхронная реплика; межконтинентальная DR-реплика асинхронная.[[7]](#source7)

Redis хранит последние 100 сообщений канала и популярные карточки, но не всю историю. Кеш карточек — cache-aside с TTL до 5 с; от stampede защищает один выполняющийся запрос на ключ. Redis Cluster распределяет ключи по hash slots, клиент обрабатывает перенаправления.[[8]](#source8) Для Kafka порядок задан партицией, а RF и ISR определяют устойчивость журнала.[[9]](#source9)

Сегменты live имеют длину 2 секунды. Для VOD по 30 сегментов одного качества объединяются в минутный объект, а компактный манифест хранит индекс byte ranges. HLS-плейлист формируется из этого индекса. Это уменьшает число объектов до 3,024 млрд за 7 суток, сохраняя 2-секундную выдачу зрителю. Клипы создаются отдельными файлами и не зависят от удаления исходного VOD.

Ceph хранит бинарные данные с erasure coding 8+3: физический множитель одной копии — 11/8 = 1,375.[[10]](#source10) Вторую независимую региональную копию нужно учитывать дополнительно. Для 75,53 Пбайт логических медиаданных две копии с EC занимают примерно 207,7 Пбайт, без свободного места и backup. Для профиля EC по стойкам требуется не менее 11 доменов размещения.

### 6.4. Подключения и клиентские библиотеки

| Хранилище | Интеграция из Go | Балансировка и ограничение подключений |
|---|---|---|
| PostgreSQL | `pgx/v5`, `pgxpool` | PgBouncer transaction pooling; отдельные endpoints primary/read-only; до 300 активных server connections на БД |
| Redis Cluster | `redis/go-redis` | Подключение по slot map; pipeline для добавления и ограничения хвоста чата |
| Kafka | `twmb/franz-go` | Bootstrap через несколько брокеров, далее соединение с leader партиции; idempotent producer |
| Ceph RGW | AWS SDK for Go v2, S3 API | Пул HTTPS keep-alive, несколько RGW за внутренним балансировщиком |

Записи, авторизация, refresh token и чтение сразу после изменения идут на primary. Остальные SQL-чтения могут обслуживаться локальной standby; при большом отставании запрос возвращается на primary. На соединения приложения устанавливаются лимиты и таймауты, чтобы всплеск запросов не создавал тысячи PostgreSQL-процессов.

| Компонент | Резервирование | Backup и восстановление |
|---|---|---|
| Core DB и Chat Master DB | Primary + sync-standby в другой стойке Франкфурта; async DR в Ашберне | Полный backup еженедельно, differential ежедневно, непрерывный WAL archive; хранение 30 суток в отдельном backup-bucket; PITR |
| Redis | Реплика на каждый master | Кеш восстанавливается из SQL/событий; для реестра достаточно новых heartbeat |
| Kafka | RF=3, минимум две ISR; журнал чата дополнительно копируется в DR-регион | Retention 24 ч для повторной обработки; это буфер, а не backup 30-дневной истории |
| Ceph: VOD | EC 8+3 и async-копия в парный регион | Откат ошибочного явного удаления в течение 24 ч; после планового TTL 7 суток восстановление не обещается |
| Ceph: клипы и изображения | EC и региональная копия | Versioning и защита удалённых версий 30 суток; доступ backup-оператора отделён от приложения |
| Live/CDN/WS-буферы | Live — две копии; остальное восстанавливается | Долговременные backup не нужны; live — из входящего потока, CDN — из origin, WS — после переподключения |

Реплика не заменяет backup при ошибочном удалении. При полном отказе Франкфурта резервная БД повышается в Ашберне только после fencing старого primary; затем включается резервный API. Межрегиональная репликация асинхронная, поэтому RPO зависит от фактического lag. Целевые показатели: до 5 с для DR-реплики и 5–15 минут на переключение; это требования к проекту, которые нужно проверить учениями.

Для SQL резервируется дополнительно 60–100% размера строк под индексы и служебные данные. При расчёте серверов отдельно добавляются WAL, backup и не менее 20% свободного диска. Раз в месяц выполняется пробное восстановление БД и выборочная проверка файлов.
